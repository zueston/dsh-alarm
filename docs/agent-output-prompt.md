# 报警提醒 · Agent 输出约束（可直接粘进 system prompt）

> 用途：把下面「规则块」整段粘到 agent 的 system prompt / 项目 `AGENTS.md` 里。
> 目标：**该响的一次不落（不漏报），不该响的一次不响（不误报）**。
> 判定实现在 `lib/alarm.js`；本文件是它的「输入端契约」。

---

## 规则块（从这里开始复制）

```text
【报警提醒输出约束】你用 DSH 的 dsh-alarm 插件与人协作。它只根据「你这一轮最后一条回复的正文」
和「你调用的工具」来判断事件，因此你必须按下面的规则输出，否则会漏报或误报。

R1 通道：只有「该轮最后一条回复的正文」参与判定。思考链/推理段、工具调用参数、工具返回、
   围栏代码块（```...```）内的文字一律不算。要表达的信号必须写进正文，且不要包在代码块里。

R2 一消息一结论：同一条回复只承载一个「事件结论」。同时说多件事会导致节流/闩锁互相吞掉。

R3 裁决事件：需要人在多个选项里做选择时，必须调用 ask_user_question 工具；
   不要用「请问你要 A 还是 B」这类纯文本代替（纯文本不会触发提醒）。

R4 计划事件：需要人确认方案/计划时，必须调用 exit_plan_mode 工具。

R5 完成事件：全部任务真正完成时，必须调用 update_goal 且 action="complete"。
   在正文里写「全部完成了」不会触发；普通轮次结束也不会触发。

R6 待人工测试：需要人实测时，必须把任务包状态文件的「当前阶段」改成「待人工测试」，
   路径形如 03-开发协同/<任务名>/状态.md，行内容形如：当前阶段：待人工测试
   判定看文件的真实相位变化（写前不是该值、写后 1.2 秒复读仍是该值才响），
   不看你在对话里写什么；同一文件 5 分钟内只响一次。

R7 重启事件（最容易误判，必须严格遵守）：
   R7.1 必须说：动作词 + 对象 + 现在时三要素齐备。
         认可写法：现在可以重启 DSH。/ 请重启 DSH 后按下面步骤验证。/ 改动需要重启 DSH 才生效。
                  重启客户端后生效。/ Restart DSH to apply.
         简写也认：需要重启 / 请重启 / 重启后生效（单独成句）。
         对象可用：DSH、dsh、客户端、软件、程序、应用；英文 dsh / app / client。
   R7.2 禁止说（这些都会被过滤，等于没提醒）：
         否定式：不需要、无须、无需、不必、不用、不要、别、勿、暂不、先不、不能、不会、
                 不打算、不准备 + 「重启」；
         未来时：等、待、再通知、通知你、告诉你、稍后、之后、回头、改完、完成后、收尾后、
                 搞定后 + … + 「重启」；
         代码块里、思考链里、工具参数里。
   R7.3 一句只保留一种重启表述：要么肯定一次，要么否定一次，不要「不用重启…但下次要重启」混着写。
   R7.4 确实不需要重启时，明确写「这次不需要重启 DSH」即可（会被正确过滤，不会误报）。

R8 结束/中断/报错：这三类由这一轮「怎么收尾」决定，不可用文字伪造；
   不要为了触发提醒去写假的结束语。

R9 禁止伪造信号：不要空转 update_goal(complete)、不要写假的「当前阶段：待人工测试」、
   不要重复刷「请重启」——重复只会被节流吞掉，而且会污染诊断日志与进度台账。

R10 收尾前自检（逐条过，任一条不满足就改）：
   ① 这件事有专用工具吗（裁决/计划/完成）？有就用工具，别用文字。
   ② 结论句是否完整落在最后一条回复的正文里，且没被代码块包住？
   ③ 若说了重启：动作词 + 对象 + 现在时是否齐备？是否混入了否定式或未来时？
   ④ 若说了「待人工测试」：状态文件里的「当前阶段」是否真的改成了「待人工测试」？
   ⑤ 这一条回复是否塞了两个以上结论？是则拆开。
   ⑥ 是否在用重复表述「确保它响」？停，静默也会到达。

R11 交付口径：把结论放在回复的最后一段（正文），不要藏在长文的开头或中间；
   需要人行动时，明确写出「请你做什么」+「怎么回话」，与报警事件一一对应。
```

## 附：为什么是这些规则（给人看的，不用粘进 prompt）

| 规则 | 对应的插件判据 | 违反后的症状 |
|---|---|---|
| R1 | 只读最后一条 assistant 消息的 `text` part（`assistantTextOf` / `isReasoningPart`） | 写在推理或代码块里 → **漏报** |
| R3 / R4 | `TOOL_KINDS`（`ask_user_question` / `exit_plan_mode`） | 用文字问 → **漏报** |
| R5 | `update_goal(action="complete")` 专用分支 | 只写「完成了」→ **漏报**；普通轮次结束也不响 |
| R6 | `PHASE_RE` + 写前/写后 1.2s 复读 + 5 分钟同文件去重 | 只写文字 / 写错字段名 → **漏报**；反复重写同一值 → 无意义 |
| R7.1 | `RESTART_RE` | 少一个要素 → **漏报** |
| R7.2 | `NEGATED_RESTART_RE`、`FUTURE_RESTART_RE`、`FENCED_CODE_RE` | 说「不需要重启」却被当成要重启 → **误报**（过滤后不会）；写「等改完再重启」→ 被整段摘掉 → **漏报** |
| R7.3 | 否定过滤会连带吃掉后面 ≤12 个字符 | 实测：`不需要重启 DSH，但下次要重启客户端。` → 判定为**不命中**（`重启客户端` 被否定式连带摘掉）→ **漏报**。所以一轮只留一处重启表述 |
| R2 / R9 | 同 kind 4s 节流、裁决后 15s 闩锁 | 一条回复两个结论 → 其中一条被吞 |
| R8 | `turn/end` 的 `reason` 分类（`INTERRUPT_RE`） | 用文字假装结束 → 无效果 |

## 附：最短可用版（只要 8 行，空间紧张时用）

```text
报警提醒输出约束：①只有这一轮最后一条回复的正文会被判定，思考链/工具参数/代码块不算。
②要人裁决用 ask_user_question，要人确认计划用 exit_plan_mode，任务完成用 update_goal(action=complete)。
③要人实测就把 03-开发协同/<任务>/状态.md 的「当前阶段」改成「待人工测试」。
④要人重启就写「现在可以重启 DSH」这类句子：动作词+对象+现在时；不要写「不需要重启/等改完再重启」。
⑤一条回复只放一个结论，不要重复刷，不要伪造信号。
```
